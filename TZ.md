## 2. НАЗНАЧЕНИЕ И ЦЕЛИ СОЗДАНИЯ СИСТЕМЫ

### 2.1. Назначение системы
Веб-приложение "Expense Tracker" предназначено для ведения учета личных финансов, анализа расходов и доходов, планирования бюджета и формирования финансовых отчетов.

### 2.2. Цели создания системы
- Обеспечить удобный инструмент для учета всех финансовых операций пользователя
- Предоставить визуализацию финансовых данных через графики и диаграммы
- Помочь пользователям контролировать расходы и планировать бюджет
- Сформировать финансовую отчетность за различные периоды

### 2.3. Целевая аудитория
- Студенты, контролирующие личный бюджет
- Работающие специалисты для планирования расходов
- Семьи для ведения семейного бюджета
- Люди, заботящиеся о финансовой грамотности

## 3. ХАРАКТЕРИСТИКА ОБЪЕКТА АВТОМАТИЗАЦИИ

### 3.1. Описание объекта
Объектом автоматизации является процесс управления личными финансами, включающий:
- Регистрацию доходов и расходов
- Категоризацию финансовых операций
- Анализ финансового состояния
- Планирование и контроль бюджета

### 3.2. Участники процесса

2. Добавление/редактирование/удаление транзакций

4. Просмотр аналитики и отчетов

6. Экспорт данных для внешнего анализа

## 4. ТРЕБОВАНИЯ К СИСТЕМЕ

### 4.1. Требования к функциональным характеристикам

#### 4.1.1. Модуль "Управление пользователями"

**FR-1.1. Регистрация пользователя**
- Система должна позволять новому пользователю зарегистрироваться
- Обязательные поля:
  - Email (уникальный)
  - Пароль (минимум 8 символов)
  - Подтверждение пароля
  - Имя
  - Фамилия
- Опциональные поля:
  - Валюта по умолчанию (RUB, USD, EUR)
- Система должна проверять уникальность email
- Система должна валидировать формат email
- Пароль должен храниться в хешированном виде (BCrypt)

**FR-1.2. Авторизация пользователя**
- Система должна обеспечивать вход пользователя по email и паролю
- При успешной авторизации система генерирует JWT токен
- Токен используется для доступа к защищенным endpoints
- Время жизни токена: 24 часа
- Система должна обеспечивать механизм обновления токена (refresh token)

**FR-1.3. Управление профилем**
- Пользователь должен иметь возможность:
  - Просматривать свои данные
  - Редактировать имя и фамилию
  - Изменять валюту по умолчанию
  - Менять пароль (с вводом старого пароля)
- Система должна валидировать все изменения

**FR-1.4. Выход из системы**
- Пользователь должен иметь возможность выйти из системы
- При выходе токен должен стать недействительным

#### 4.1.2. Модуль "Управление категориями"

**FR-2.1. Предустановленные категории**

Система должна автоматически создавать базовые категории при регистрации:

**Категории расходов (EXPENSE):**
- Продукты питания (Food) - цвет: #FF6B6B
- Транспорт (Transport) - цвет: #4ECDC4
- Жилье (Housing) - цвет: #45B7D1
- Развлечения (Entertainment) - цвет: #FFA07A
- Здоровье (Health) - цвет: #98D8C8
- Одежда (Clothing) - цвет: #F7DC6F
- Образование (Education) - цвет: #BB8FCE
- Прочее (Other) - цвет: #95A5A6

**Категории доходов (INCOME):**
- Зарплата (Salary) - цвет: #27AE60
- Фриланс (Freelance) - цвет: #2ECC71
- Инвестиции (Investment) - цвет: #58D68D
- Подарки (Gifts) - цвет: #82E0AA
- Прочее (Other) - цвет: #ABEBC6

**FR-2.2. Создание пользовательских категорий**
- Пользователь должен иметь возможность создать свою категорию
- Обязательные поля:
  - Название категории (уникальное для пользователя)
  - Тип (INCOME / EXPENSE)
- Опциональные поля:
  - Цвет (HEX формат)
  - Иконка (название из Font Awesome или эмодзи)
- Система должна проверять уникальность названия для данного пользователя

**FR-2.3. Редактирование категорий**
- Пользователь может редактировать только свои пользовательские категории
- Предустановленные категории редактировать нельзя
- Можно изменить: название, цвет, иконку
- Нельзя изменить: тип (INCOME/EXPENSE)

**FR-2.4. Удаление категорий**
- Пользователь может удалять только свои пользовательские категории
- Предустановленные категории удалять нельзя
- При удалении категории:
  - Если есть транзакции - категорию нельзя удалить (ошибка)
  - Если нет транзакций - категория удаляется
- Альтернатива: перемещение транзакций в "Прочее" перед удалением

**FR-2.5. Просмотр категорий**
- Пользователь должен видеть список всех своих категорий
- Возможность фильтрации по типу (все / доходы / расходы)
- Отображение информации: название, тип, цвет, количество транзакций
- Сортировка: по названию, по типу, по дате создания

#### 4.1.3. Модуль "Управление транзакциями"

**FR-3.1. Создание транзакции**
- Пользователь должен иметь возможность добавить транзакцию
- Обязательные поля:
  - Тип (INCOME / EXPENSE)
  - Сумма (положительное число, до 2 знаков после запятой)
  - Категория (выбор из списка категорий пользователя)
  - Дата транзакции
- Опциональные поля:
  - Описание (до 500 символов)
  - Теги (список, разделенный запятыми)
- Система автоматически сохраняет:
  - Дату создания записи
  - Дату последнего изменения
  - ID пользователя

**FR-3.2. Просмотр списка транзакций**
- Система должна отображать все транзакции пользователя
- Формат отображения: таблица/список
- Колонки:
  - Дата
  - Тип (иконка/цвет)
  - Категория
  - Сумма (зеленый для доходов, красный для расходов)
  - Описание (кратко)
  - Действия (кнопки редактирования/удаления)
- Пагинация: по 20 записей на странице
- Сортировка по умолчанию: по дате (новые сверху)

**FR-3.3. Фильтрация транзакций**

Система должна предоставлять фильтры:

**По типу:**
- Все транзакции
- Только доходы
- Только расходы

**По категории:**
- Мультивыбор категорий

**По периоду:**
- Сегодня
- Эта неделя
- Этот месяц
- Этот год
- Произвольный период (дата от - дата до)
- Последние 30 дней
- Последние 90 дней

**По сумме:**
- От (минимальная сумма)
- До (максимальная сумма)

**По тегам:**
- Выбор одного или нескольких тегов

**По тексту:**
- Поиск в описании транзакции

Фильтры должны работать в комбинации (логическое И)

**FR-3.4. Сортировка транзакций**
- По дате (возрастание/убывание)
- По сумме (возрастание/убывание)
- По категории (алфавит)
- По дате создания записи

**FR-3.5. Редактирование транзакции**
- Пользователь может редактировать любую свою транзакцию
- Можно изменить все поля кроме ID
- Система сохраняет дату последнего изменения
- Валидация данных как при создании

**FR-3.6. Удаление транзакции**
- Пользователь может удалить любую свою транзакцию
- Перед удалением запрос подтверждения
- Удаление физическое (из базы данных)
- Альтернатива: мягкое удаление (флаг deleted)

**FR-3.7. Просмотр детальной информации**
- Клик по транзакции открывает детальную информацию:
  - Все поля транзакции
  - Дата создания записи
  - Дата последнего изменения
  - Возможность редактирования/удаления

#### 4.1.5. Модуль "Управление бюджетом"

**FR-5.1. Создание бюджета**
- Пользователь должен иметь возможность установить бюджет на категорию
- Обязательные поля:
  - Категория (только категории расходов)
  - Лимит суммы
  - Период (MONTHLY / YEARLY)
  - Дата начала
- Система автоматически рассчитывает дату окончания на основе периода
- На одну категорию может быть только один активный бюджет
- Валидация: лимит должен быть положительным числом

**FR-5.2. Просмотр бюджетов**
- Отображение списка всех бюджетов пользователя
- Для каждого бюджета отображается:
  - Название категории
  - Лимит
  - Потрачено (сумма транзакций за период)
  - Остаток (лимит - потрачено)
  - Процент использования
  - Период действия
  - Статус (активен/истек)
- Визуальный индикатор (прогресс-бар):
  - Зеленый: 0-70%
  - Желтый: 71-90%
  - Красный: 91-100%
  - Темно-красный: >100%

**FR-5.3. Расчет статуса бюджета**
Система должна автоматически рассчитывать:
- Сумму расходов по категории за период бюджета
- Процент использования = (Потрачено / Лимит) × 100
- Остаток = Лимит - Потрачено
- Количество дней до окончания периода

**FR-5.4. Уведомления о бюджете (опционально)**
- При достижении 80% лимита - предупреждение
- При достижении 100% лимита - критическое предупреждение
- При превышении лимита - уведомление о превышении
- Отображение на Dashboard

**FR-5.5. Редактирование бюджета**
- Пользователь может изменить:
  - Лимит суммы
  - Дату начала (только будущие бюджеты)
- Нельзя изменить:
  - Категорию (нужно создать новый бюджет)
  - Период (нужно создать новый бюджет)

**FR-5.6. Удаление бюджета**
- Пользователь может удалить любой свой бюджет
- Удаление не влияет на транзакции
- Запрос подтверждения перед удалением

**FR-5.7. История бюджетов**
- Просмотр истекших бюджетов
- Отображение результатов выполнения:
  - Выполнен (не превышен лимит)
  - Превышен (с указанием на сколько)

**REL-1. Доступность системы**
- Система должна быть доступна 99% времени работы (для локального развертывания)

**REL-2. Обработка ошибок**
- Все исключения должны быть перехвачены и обработаны
- Пользователю должны отображаться понятные сообщения об ошибках
- Критические ошибки должны логироваться

**REL-3. Целостность данных**
- Система должна обеспечивать целостность данных при любых операциях
- Транзакции базы данных должны быть атомарными
- При ошибке операции данные должны откатываться к предыдущему состоянию

**REL-4. Резервное копирование**
- Рекомендация пользователю делать регулярные бэкапы через экспорт данных
- Система должна поддерживать экспорт всех данных

### 4.3. Требования к безопасности

**SEC-1. Аутентификация**
- Доступ к системе только для авторизованных пользователей
- Использование JWT токенов для аутентификации
- Токены должны иметь ограниченный срок жизни (24 часа)
- Механизм refresh token для обновления сессии

**SEC-2. Авторизация**
- Пользователь может видеть и изменять только свои данные
- Проверка прав доступа на уровне сервисов
- Запрет доступа к чужим ресурсам (HTTP 403)

**SEC-3. Защита паролей**
- Пароли должны храниться в хешированном виде (BCrypt)
- Минимальная длина пароля: 8 символов
- Валидация сложности пароля (буквы, цифры)

**SEC-4. Защита от SQL Injection**
- Использование Prepared Statements (через JPA)
- Валидация всех входных данных
- Запрет на выполнение произвольных SQL запросов

**SEC-5. Защита от XSS**
- Экранирование всех пользовательских данных при выводе
- Content Security Policy заголовки
- Валидация входных данных

**SEC-6. CORS настройки**
- Настройка разрешенных источников для API запросов
- Ограничение методов и заголовков
- Разрешение cookies для аутентификации

**SEC-7. HTTPS**
- Рекомендация использования HTTPS для продакшн окружения
- Защита передачи данных (токены, пароли)

---

### 4.4. Требования к производительности

**PERF-1. Время отклика**
- Простые операции (CRUD): не более 200ms
- Сложные запросы (аналитика): не более 1 секунды
- Загрузка страницы: не более 2 секунд

**PERF-2. Пропускная способность**
- Поддержка не менее 100 одновременных пользователей

**PERF-3. Оптимизация запросов**
- Использование индексов на часто запрашиваемых полях
- Lazy loading для связанных сущностей
- Пагинация для больших списков данных

**PERF-4. Кэширование**
- Кэширование справочных данных (категории)
- Кэширование результатов аналитики (опционально)

## 5. ТЕХНИЧЕСКИЕ РЕШЕНИЯ

### 5.1. Архитектура системы

**Тип архитектуры:** Monolithic (монолитная)

**Архитектурный паттерн:** Layered Architecture (многослойная)

```
┌─────────────────────────────────────────────┐
│         PRESENTATION LAYER                  │
│  ┌────────────┐  ┌────────────────────┐    │
│  │ REST API   │  │  Thymeleaf Views   │    │
│  │ Controllers│  │  (опционально)     │    │
│  └────────────┘  └────────────────────┘    │
└─────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│            SERVICE LAYER                     │
│  ┌──────────────┐  ┌──────────────────┐    │
│  │ Business     │  │  DTO Mapping     │    │
│  │ Logic        │  │  (MapStruct)     │    │
│  └──────────────┘  └──────────────────┘    │
└─────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│          REPOSITORY LAYER                    │
│  ┌──────────────┐  ┌──────────────────┐    │
│  │ Spring Data  │  │  Custom Queries  │    │
│  │ JPA          │  │                  │    │
│  └──────────────┘  └──────────────────┘    │
└─────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│              DATABASE                        │
│            PostgreSQL                        │
└─────────────────────────────────────────────┘
```

**Дополнительные компоненты:**
- Security Layer (Spring Security + JWT)
- Exception Handling (Global Exception Handler)
- Validation Layer (Bean Validation)

### 5.3. Модель данных

#### 5.3.1. Сущности (Entities)

**Entity: User**
```java
@Entity
@Table(name = "users")
class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    Long id;
    
    @Column(unique = true, nullable = false)
    String email;
    
    @Column(nullable = false)
    String password; // BCrypt hash
    
    @Column(nullable = false)
    String firstName;
    
    @Column(nullable = false)
    String lastName;
    
    @Enumerated(EnumType.STRING)
    Currency defaultCurrency; // RUB, USD, EUR
    
    @CreationTimestamp
    LocalDateTime createdAt;
    
    // Relations
    @OneToMany(mappedBy = "user")
    List<Category> categories;
    
    @OneToMany(mappedBy = "user")
    List<Transaction> transactions;
    
    @OneToMany(mappedBy = "user")
    List<Budget> budgets;
}
```

**Entity: Category**
```java
@Entity
@Table(name = "categories")
class Category {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    Long id;
    
    @Column(nullable = false)
    String name;
    
    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    TransactionType type; // INCOME, EXPENSE
    
    String color; // HEX формат
    
    String icon;
    
    @Column(nullable = false)
    Boolean isDefault; // true для предустановленных
    
    @ManyToOne
    @JoinColumn(name = "user_id", nullable = false)
    User user;
    
    @CreationTimestamp
    LocalDateTime createdAt;
    
    // Relations
    @OneToMany(mappedBy = "category")
    List<Transaction> transactions;
}
```

**Entity: Transaction**
```java
@Entity
@Table(name = "transactions")
class Transaction {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    Long id;
    
    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    TransactionType type; // INCOME, EXPENSE
    
    @Column(nullable = false)
    BigDecimal amount; // Точные вычисления
    
    @ManyToOne
    @JoinColumn(name = "category_id", nullable = false)
    Category category;
    
    @ManyToOne
    @JoinColumn(name = "user_id", nullable = false)
    User user;
    
    @Column(nullable = false)
    LocalDate date;
    
    @Column(length = 500)
    String description;
    
    @ElementCollection
    @CollectionTable(name = "transaction_tags")
    List<String> tags;
    
    @CreationTimestamp
    LocalDateTime createdAt;
    
    @UpdateTimestamp
    LocalDateTime updatedAt;
}
```

**Entity: Budget**
```java
@Entity
@Table(name = "budgets")
class Budget {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    Long id;
    
    @ManyToOne
    @JoinColumn(name = "category_id", nullable = false)
    Category category;
    
    @ManyToOne
    @JoinColumn(name = "user_id", nullable = false)
    User user;
    
    @Column(nullable = false)
    BigDecimal limitAmount;
    
    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    BudgetPeriod period; // MONTHLY, YEARLY
    
    @Column(nullable = false)
    LocalDate startDate;
    
    @Column(nullable = false)
    LocalDate endDate;
    
    @CreationTimestamp
    LocalDateTime createdAt;
}
```

### 5.4. REST API Структура

**Base URL:** `/api/v1`

#### Authentication Endpoints
- `POST /api/v1/auth/register` - Регистрация
- `POST /api/v1/auth/login` - Вход
- `POST /api/v1/auth/refresh` - Обновление токена
- `POST /api/v1/auth/logout` - Выход

#### User Endpoints
- `GET /api/v1/users/me` - Получить профиль
- `PUT /api/v1/users/me` - Обновить профиль
- `PUT /api/v1/users/me/password` - Сменить пароль

#### Category Endpoints
- `GET /api/v1/categories` - Список категорий (query: type)
- `GET /api/v1/categories/{id}` - Получить категорию
- `POST /api/v1/categories` - Создать категорию
- `PUT /api/v1/categories/{id}` - Обновить категорию
- `DELETE /api/v1/categories/{id}` - Удалить категорию

#### Transaction Endpoints
- `GET /api/v1/transactions` - Список транзакций (+ filters)
- `GET /api/v1/transactions/{id}` - Получить транзакцию
- `POST /api/v1/transactions` - Создать транзакцию
- `PUT /api/v1/transactions/{id}` - Обновить транзакцию
- `DELETE /api/v1/transactions/{id}` - Удалить транзакцию
- `GET /api/v1/transactions/export/excel` - Экспорт Excel
- `GET /api/v1/transactions/export/csv` - Экспорт CSV

#### Analytics Endpoints
- `GET /api/v1/analytics/dashboard` - Dashboard данные
- `GET /api/v1/analytics/by-category` - По категориям
- `GET /api/v1/analytics/by-period` - По периодам
- `GET /api/v1/analytics/comparison` - Сравнение периодов
- `GET /api/v1/analytics/trends` - Тренды

#### Budget Endpoints
- `GET /api/v1/budgets` - Список бюджетов
- `GET /api/v1/budgets/{id}` - Получить бюджет
- `POST /api/v1/budgets` - Создать бюджет
- `PUT /api/v1/budgets/{id}` - Обновить бюджет
- `DELETE /api/v1/budgets/{id}` - Удалить бюджет
- `GET /api/v1/budgets/{id}/status` - Статус выполнения
